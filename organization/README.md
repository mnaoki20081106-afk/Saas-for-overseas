| 旧役職 | 統合先 |
| --- | --- |
| CEO | **諭吉（CEO）** |
| Analyst（企画・分析） | **諭吉**（優先順位の決定に統合） |
| Researcher（案件調査） | **サラ（CMO）** |
| Designer（ピン設計） | **サラ（CMO）** |

| Writer（執筆） | **ケン（CTO）** |
| Editor（英語検品） | **ケン（CTO）** ＋ 諭吉の独立読み |
| QA（最終検品） | **ケン（CTO）** ＋ 諭吉の独立読み |

## この統合で失うもの（正直に書きます）

旧構成では、**書き手（Writer）と検品者（Editor）を別人格にしていました。**
自分が書いた文章を自分で検品すると、無意識に擁護してしまうからです。

3層構造では、ケンが書いて、ケンが検品します。**この独立性は落ちます。**

### だから、こう補います

**検品を「下」ではなく「上」に移しました。**

1. **機械の検品は落とさない。** `co writer:check` が語数・見出し・比較表・リンク数・
   禁止表現・西暦・重複を機械的に検査します。ここは人格と無関係に効きます。
2. **ケンは、書いた直後に検品しない。** 一度離れてから、読者として通しで読み直します。
   手順は [cto.md](cto.md) の「セルフ検品」に固定してあります。
3. **諭吉が、オーナーに出す前に独立して読む。** 諭吉は本文を書いていないので、
   読者に近い目で読めます。**部下を増やさずに、第二の目を確保しました。**

それでも旧構成より弱いのは事実です。記事が10本を超えて品質のばらつきが見えてきたら、
検品のやり方を見直す提案を諭吉からオーナーに出します。

## 連携のしかた

```
諭吉が朝、会社の状態を読む（npm run co -- status）
   ↓
諭吉が今日やることを決める
   ↓
   ├──→ サラに指示（案件を調べる／ピンを作る）      ┐
   └──→ ケンに指示（記事を書く／検品する）          ├ 並行して進む
                                                    ┘
   ↓
二人の成果物が data/ と content/ に残る
   ↓
諭吉が取りまとめ、リスクを添えて、A案/B案 か GO/STOP でオーナーに出す
   ↓
オーナーが押す
   ↓
GitHub Actions が実行（投稿・公開）
```

**サラとケンは互いに直接やり取りしません。** 全部 `data/` に残し、諭吉が繋ぎます。
理由：口頭の申し送りは記録に残らず、後から「なぜそうしたか」が追えなくなるからです。
