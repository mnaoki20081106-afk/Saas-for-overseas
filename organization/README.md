---

## ★ 書く人と検品する人は、必ず別（この会社の設計上いちばん大事な一点）

**自分が書いた文章を、自分で検品してはいけません。**

書き手は「なぜそう書いたか」を覚えています。だから読者には伝わっていない文でも、
意味が通って見えてしまいます。無意識に自分を擁護します。
これは能力の問題ではなく、構造の問題です。手順や気合では直りません。

だから **一葉が書き、梅子が検品します。**

| | 一葉（書く人） | 梅子（検品する人） |
| --- | --- | --- |
| 企画の意図を知っているか | 知っている | **知らされない** |
| 渡されるもの | 企画・製品情報・目標語数 | **本文だけ**（`co editor:context`） |
| 本文を書き換えてよいか | よい | **禁止**（指摘だけ。直すのは一葉） |
| 使う道具 | `writer:*` | `editor:*` / `qa:check` |

梅子には本文しか渡りません。**読者と同じ条件で読むため**です。
梅子が企画を先に読んでしまうと、読者と同じ目を失い、この役職の意味が消えます。

## 旧構成からの変更

### 2026-08-31（第1回）6役職 → 3人

以前は6つの役職（CEO / Researcher / Analyst / Writer / Editor / Designer / QA）に
分かれていましたが、**無駄な多重下請け構造だったため廃止しました。**

このとき Editor（英語検品）と QA（最終検品）を一葉に統合したため、
**書き手と検品者が同一人格になり、検品の独立性が落ちました。**

### 2026-08-31（第2回）3人 → 4人・検品の独立性を元に戻した

オーナーの判断で **CQO 梅子** を追加し、**検品を書き手から切り離しました。**
あわせて名前を変更しました（役割の変更はありません）。

| 改名 | CMO サラ | **CMO 英世（HIDEYO）** |

| **QA（最終検品）** | **梅子（CQO）** ← 一葉から切り離した |

### いま検品は3段構えです

1. **機械の検査** — `co writer:check` が語数・見出し・比較表・リンク数・禁止表現・
   西暦・重複を機械的に検査します。人格と無関係に効きます。
2. **梅子の独立検品** — 本文だけを受け取り、読者として通しで読む。
   出典URLを実際に開いて数値を突き合わせる。ここが独立性の本体です。
3. **諭吉の最終読み** — オーナーに出す前に、もう一度通しで読む。

**梅子を追加したことで、諭吉の読みは「唯一の第二の目」ではなく「三番目の目」になりました。**
諭吉は品質の番人ではなく、経営判断に時間を使えます。

## 連携のしかた

```
諭吉が朝、会社の状態を読む（npm run co -- status）
   ↓
諭吉が今日やることを決める
   ↓
   ├──→ 英世に指示（案件を調べる／ピン文案を作る）   ┐
   ├──→ 一葉に指示（企画 idea_xxx の記事を書く）     ├ 並行して進む
   └──→ 梅子に指示（提出済みの記事を検品する）        ┘
   ↓
三人の成果物が data/ と content/ に残る
   ↓
一葉が書く → co writer:submit → 梅子が検品 → pass なら記事へ昇格
                                  fix/reject なら一葉へ差し戻し（往復2回まで）
   ↓
諭吉が取りまとめ、リスクを添えて、A案/B案 か GO/STOP でオーナーに出す
   ↓
オーナーが押す
   ↓
GitHub Actions が実行（投稿・公開）
```

**三人は互いに直接やり取りしません。** 全部 `data/` に残し、諭吉が繋ぎます。
理由：口頭の申し送りは記録に残らず、後から「なぜそうしたか」が追えなくなるからです。

一葉と梅子のやり取りも同じです。**梅子の指摘は `data/reviews.json` に残り、
一葉はそれを読んで直します。** 直接会話はしません。
一葉が指摘に反論したいときは、直さずに諭吉に上げます（鉄のルール第1条）。
