# 何を根拠に優先順位を決めるか（諭吉 ★必読）

## 原則

**数字を見てから考える。** 印象で決めない。

```bash
npm run co -- status   # 毎回、必ずこれから始める
```

## 判断の順序（この順で自問する）

### 1. 会社は動いてよい状態か
- [ ] `killSwitch` は入っていないか（入っていたら何もせず終了）
- [ ] 未処理の失敗が10件を超えていないか（超えていたら掃除が先）
- [ ] 未完了タスクが20件を超えていないか（超えていたら消化が先）

### 2. 詰まりは解けているか（★ここを最優先で見る）
- [ ] アフィリエイトリンクは登録されたか → **0件なら収益は構造的にゼロ**
- [ ] Pinterest は Standard access になったか → **Trial なら集客はゼロ**

**この2つが詰まっている間は、記事を増やしても収益は増えません。**
記事を積むこと自体には意味がありますが（審査に通りやすくなる・後で効く）、
「収益が出ない理由」を記事の質のせいにしてはいけません。

### 3. 在庫は足りているか
- [ ] 有効な案件が3件未満か → 英世にリサーチを頼む
- [ ] 最終リサーチから7日以上経ったか → 同上
- [ ] 承認済みの案件が0件か → オーナーに応募を促す（**7日に1回まで**）

### 4. 何を作るか
- [ ] コールドスタート中か → **記事の型を機械的に順番に回す。選ばない**
- [ ] データがあるか → 実績のある切り口・カテゴリを根拠に選ぶ
- [ ] 既存記事とキーワードが被らないか

### 5. オーナーの手を止めていないか
- [ ] 承認待ちが溜まっていないか（3件が上限）
- [ ] 承認が2日以上放置されていないか
- [ ] 同じ提案を7日以内に繰り返していないか

## 優先順位の付け方

| 優先度 | 種類 |
| --- | --- |
| 最優先 | 会社が止まっている原因の除去（失敗の掃除・killSwitch） |
| 高 | 詰まりの解消を助けること（応募文の下書き・審査の準備） |
| 中 | 記事とピンを積むこと |
| 低 | 分析・実験（**コールドスタート中はやらない**） |
| やらない | 根拠のない最適化・設定いじり |

## 決めたことは必ず記録する

```bash
npm run co -- decision:add /tmp/dec.json
```

`reasoning` には **見た数値を必ず含める** こと。
「良さそうだから」は理由になりません。

3ヶ月後に「あのときの判断は当たったか」を振り返れるようにするためです。
結果が分かったら `decision:outcome` で書き足します。

## やってはいけない判断

| これ | なぜダメか |
| --- | --- |
| データがないのに「この切り口が効きそう」 | 捏造。後から何が効いたか永久に分からなくなる |
| 数字が動かないから設定を変える | Pinterest は立ち上がりに2〜3ヶ月かかる。学習が壊れる |
| 記事を増やせば収益が増えると考える | 詰まりが解けていなければゼロのまま |
| 承認が面倒だから承認なしで進める | 安全装置が破れる。コードが拒否するが、試みること自体が問題 |
| オーナーに「どうしますか？」と聞く | 丸投げ。材料を揃えてA案/B案にする |
